# I18N

이 문서는 화면에 보이는 문구를 어떻게 번역 파일로 옮기고, 어떻게 읽어 오고, 한국어 문장의 줄바꿈을 어떻게 고르는지 설명한다. 화면·입력 계약 전체는 [UI_UX](UI_UX.md)가 소유하고, 이 문서는 그중 다국어 부분만 다룬다.

## 한눈에 보기

| 하고 싶은 일 | 쓰는 것 |
|---|---|
| 화면에 문구 한 줄 띄우기 | `context.translate('키')` |
| 개수에 따라 문장이 달라지는 문구 | `context.translatePlural('키', 값)` |
| 한국어 문장을 자연스럽게 줄바꿈 | `SemanticText(...)` |
| 번역 키 추가 | `assets/translations/src/<영역>/<locale>.json`을 고치고 `dart run tools/merge_translations.dart` |
| 로직에서 문구가 필요할 때 | 로직은 키만 돌려주고 화면이 번역한다 |

## 1. 번역 파일 구조

앱이 실제로 읽는 파일은 예전과 같다.

```
assets/translations/<locale>.json          앱이 읽는 파일. 생성물이다.
assets/translations/data/<locale>/*.json   Item·Jester 카탈로그. 이 문서의 대상이 아니다.
```

바뀐 것은 그 위층이다. `assets/translations/<locale>.json`은 이제 손으로 고치지 않고 영역별 조각 파일에서 만들어 낸다.

```
assets/translations/src/<영역>/<locale>.json   원본. 사람이 고치는 파일이다.
```

영역을 나눈 이유는 충돌 때문이다. 여러 사람이 동시에 수백 개의 키를 추가하는데 locale마다 파일이 하나뿐이면 모든 변경이 같은 파일에서 부딪힌다. 영역을 나누면 각자 자기 조각만 고치므로 부딪히지 않는다.

조각을 합치는 도구는 `tools/merge_translations.dart`다.

```
dart run tools/merge_translations.dart            조각을 합쳐 생성물을 다시 만든다
dart run tools/merge_translations.dart --check    생성물이 조각과 어긋나면 실패한다
```

이 도구는 다음을 강제한다.

- 키는 정렬해서 쓴다. 그래서 같은 조각에서 항상 같은 파일이 나온다.
- 두 영역이 같은 키를 정의하면 오류다.
- 한 영역 안에서 locale마다 키 집합이 다르면 오류다.

생성물은 저장소에 커밋한다. 앱이 번들에서 읽어야 하기 때문이다. 대신 `test/tools/translations_test.dart`가 생성물과 조각이 일치하는지, 5개 locale의 키 집합이 같은지, 빈 값이 없는지 검사한다. `docs/generated/`와 같은 방식이다.

`assets/translations/src/`는 앱 번들에 들어가지 않는다. `pubspec.yaml`의 `assets/translations/` 항목은 그 폴더의 직속 파일만 포함하고 하위 폴더는 포함하지 않는다. 같은 테스트가 이 조건도 검사한다.

## 2. 키 이름 규칙

- **영역 접두사 + camelCase.** 기존 132개 키가 이미 이 모양이다(`runInfoTitle`, `tutorialBattleBoardDesc`). 새 키도 같게 쓴다. 점(`.`)으로 계층을 나누지 않는다. `easy_localization`은 점이 든 키를 중첩 키로 해석하려 시도하므로 평평한 키만 쓰는 편이 예측하기 쉽다.
- **접두사는 화면이나 기능 단위**로 잡는다. `runInfo`, `shopOffer`, `bossRule`처럼 그 문구가 어디서 보이는지 알 수 있게 한다.
- **문장은 통째로 한 키에 둔다.** 조각을 이어 붙이지 않는다. 언어마다 어순이 다르기 때문이다. `'타일 ' + n + '장 생성'`처럼 나누면 영어에서는 `Draw {count} tiles`, 일본어에서는 `タイル{count}枚生成`이 되어야 하는데 조각 순서가 고정되어 버린다.
- **값 채우기는 `namedArgs`를 쓴다.** 위치 기반 `args`는 순서가 바뀌는 언어에서 어느 값이 어디에 들어가는지 읽기 어렵다.

  ```dart
  // assets/translations/src/battle/ko.json
  //   "runInfoDeckSummaryExtended": "덱 {total}장 · 추가 {added}장"
  context.translate(
    'runInfoDeckSummaryExtended',
    namedArgs: {'total': '$total', 'added': '$added'},
  );
  ```

- **숫자·단위·조사가 얽힌 문장**도 같은 규칙이다. 단위(`장`, `회`, `G`)는 문장의 일부이므로 키 값 안에 둔다. 숫자만 `namedArgs`로 넘긴다.
- **개수에 따라 문장이 달라지면 `translatePlural`을 쓴다.** 한국어는 단수·복수 구분이 없지만 영어는 있다. 이때 키 값은 형태별 하위 객체다.

  ```json
  "shopRerollRemaining": {
    "one": "Reroll {} left",
    "other": "Rerolls {} left"
  }
  ```

  한국어처럼 한 형태만 필요한 언어도 `other` 하나는 채워야 한다. 조각 파일의 값은 문자열이어야 하므로 복수형이 필요한 키는 조각을 합치는 도구를 먼저 확장해야 한다. 지금은 복수형 키가 없다.

- **영어 낱말 옆의 띄어쓰기는 언어마다 다르다(2026-09-20 사용자 결정).**
  - 중국어(简体·繁體)는 한자와 영문·숫자 사이에 반각 공백을 한 칸 둔다. 문장부호와 맞닿은 쪽, 문자열의 처음과 끝, `{placeholder}` 안쪽에는 넣지 않는다. 수량사와 백분율 기호는 숫자에 붙인다(`{count}张`, `50%`).
  - 일본어는 붙여 쓰는 것이 기본이다. 영문 고유명사로 시작하는 짧은 라벨만 띄운다(`Station クリア`). 문장 속에서는 붙인다(`Marketの所持エリア`).
  - `Gold`, `Station`, `Market`은 일본어와 중국어에서도 영어로 둔다. 일본어의 전투는 `バトル`, 중국어의 타일은 `牌`다.
  - `Chips`와 `Jester`도 일본어·중국어에서 영어로 둔다(2026-09-21 사용자 결정). 한국어 `칩`과 `Reroll Chip` 같은 고유명은 유지한다.
  - 이 규칙은 `test/tools/translations_test.dart`가 검사한다. 용어별 표와 근거는 [I18N_GLOSSARY](../tools/I18N_GLOSSARY.md)가 소유한다.

## 3. 번역을 읽는 방법

**표준은 `context.translate('키')`다.** `lib/utils/app_translation.dart`의 `BuildContext` 확장이다. `easy_localization`의 `'키'.tr()`이나 `context.tr('키')`를 화면 코드에서 직접 쓰지 않는다.

이유는 두 가지다.

첫째, **언어 전환 반응성**이다. 게임 도중에도 설정을 열어 언어를 바꿀 수 있다. `'키'.tr()`은 전역 인스턴스를 읽을 뿐 위젯 트리에 의존을 걸지 않는다. 그래서 `const` 위젯의 `build` 안에서 쓰면 부모가 다시 그려져도 그 위젯은 그대로 남아 예전 언어의 문구를 계속 보여 준다. `context.translate`는 `Localizations`를 통해 값을 찾으므로 그 의존이 걸린다. 언어가 바뀌면 `const` 위젯도 다시 그려진다. 이 차이를 `test/views/localization_switch_test.dart`가 두 라벨을 나란히 두고 증명한다.

둘째, **테스트에서 죽지 않는다**. `easy_localization`의 `context.tr()`은 조회에 실패하면 null 단언으로 죽는다. 위젯 테스트 중에는 `EasyLocalization` 조상 없이 평범한 `MaterialApp` 아래에 위젯만 띄우는 경우가 많다. `context.translate`는 그럴 때 전역 인스턴스로 떨어지고 `test/flutter_test_config.dart`가 그 전역 인스턴스에 한국어를 미리 넣어 둔다.

**전역 인스턴스로 떨어지는 분기는 테스트에서만 탄다.** 실행 중인 앱은 모든 화면을 `lib/app.dart`의 `EasyLocalization` 아래에서 만들기 때문에 `Localizations` 조회가 항상 성공한다.

공용 `showConfirmDialog`와 `showGameChoiceDialog`에는 `titleBuilder`/`messageBuilder`를 넘긴다. callback의 dialog context로 번역해야 이미 열린 dialog도 언어 변경을 따른다. 확인·취소의 기본 버튼은 인자를 생략하면 현재 언어를 사용한다. 별도 문구는 `confirmLabelBuilder`/`cancelLabelBuilder`, 선택 버튼 목록은 `actionsBuilder`로 만든다. 기존 문자열 인자는 원문을 그대로 표시하고 builder가 있으면 builder를 우선한다.

`showTopNotice`와 `showBottomNotice`도 `messageBuilder`를 받는다. overlay의 현재 context로 문구만 다시 계산하므로 언어 변경이 표시 시간이나 효과음을 다시 시작하지 않는다. 기존 문자열 인자는 번역 키로 해석하지 않고 그대로 표시한다.

## 4. 로직 계층의 문구

**로직은 번역 키를 돌려주고 화면이 그 키를 번역한다.**

`lib/logic`은 Flutter에도 번역에도 의존하지 않는다. 순수 Dart 로직 테스트와 `tools/sim`의 시뮬레이터가 `dart run`으로 도는데, 이들은 `easy_localization`을 초기화할 수 없다. 로직 안에서 `tr()`을 부르면 이 경로가 깨진다.

기존 표시 문자열은 저장 호환성을 위해 보존하고 별도 키 API를 추가한다. 로직 함수 안에서 번역을 읽거나 저장 필드를 번역 키로 바꾸지 않는다.

- `RummiBossModifier`의 `title`, `ruleText`, `markerText`와 `toJson`/`fromJson` 형식은 그대로다. `modifier.displayKeys`와 `penalty.displayKeys`는 알려진 Boss ID의 표시 키를 별도로 돌려준다. 화면은 현재 build context로 키를 번역한다.
- 알 수 없는 custom ID의 `displayKeys`는 null이다. 화면은 기존 원문을 표시하고, custom penalty의 marker가 비어 있으면 기존 score 숫자 fallback을 유지한다.
- `rummiHandRankKey(rank)`는 족보 표시 키를 반환한다. 기존 한국어 호환 함수는 모든 소비 경로를 전환하기 전까지 유지한다.
- `tools/generate_docs.dart`는 보존된 Boss 제목·규칙문으로 `docs/generated/BOSS_PATTERNS.md`를 만든다. 이 API 추가 때문에 생성기나 저장 데이터를 바꿀 필요는 없다.

`active_run_translation.dart`는 저장 요약과 난이도·슬롯 표시를 현재 context로 조합한다. `item_presentation_translation.dart`는 아이템 ID와 효과 metadata로 성공 피드백을 만든다. 정산 표시 metadata도 원래 receipt JSON과 분리하며, Jester 중복 판정은 번역된 이름에 의존하지 않는다. metadata가 없는 기존·custom 데이터는 보존된 원문으로 표시한다.

`ActionFailure`는 실패 종류와 표시 인자를 전달하고 `action_failure_translation.dart`가 화면에서 번역한다. 새 typed 명령이 null을 반환하면 성공이므로 호환용 String 명령을 다시 실행하지 않는다. Market 할인 출처와 슬롯 보너스도 typed 값으로 판단한다. 기존·custom 값의 호환 fallback은 별도로 유지한다. 표시 키 API가 준비됐다는 사실만으로 전체 다국어 전환을 완료했다고 판단하지 않는다.

## 5. 한국어 줄바꿈: SemanticText

`lib/widgets/semantic_text.dart`의 `SemanticText`는 `Text`를 그대로 바꿔 끼울 수 있는 위젯이다. 한국어 문장을 단어 중간이 아니라 의미 단위에서 끊는다.

`Text`를 **상속한다**. `data`에는 원문이 그대로 남고 `build`만 다르다. 그래서 화면의 `Text`를 `SemanticText`로 바꿔도 그 화면의 기존 테스트가 깨지지 않는다. `find.text('원문')`과 `tester.widget<Text>(...)`가 `SemanticText` 자신에 맞고, 줄바꿈이 들어간 문자열은 `Text` 위젯으로 트리에 들어가지 않는다. 접근성 label도 줄바꿈 여부와 상관없이 문장 하나로 남는다.

Flutter의 기본 줄바꿈은 한글 음절 사이에서도 줄을 끊을 수 있다. 유니코드 규칙이 그것을 허용하기 때문이다. 그래서 "감소합니다"가 "감소합"과 "니다"로 갈라지는 일이 생긴다.

### 공간 기준 선택 규칙

게임 패널은 높이가 고정돼 있어서 "몇 줄 이하"라는 기준을 글에 미리 붙일 수 없다. 줄 수는 글의 성질이 아니다. 그 상자에 배치한 결과다. 그래서 위젯은 자기가 실제로 받은 공간에서 다음 순서로 고른다.

1. 띄어쓰기에서만 끊는다고 할 때, 그 너비에서 가능한 **최소 줄 수**를 구한다.
2. 그 최소 줄 수를 쓰는 배치들 중에서만 가장 자연스러운 끊는 자리를 고른다. 줄 하나를 더 써서 더 예쁘게 끊는 일은 하지 않는다.
3. 그 배치조차 `maxLines`나 주어진 높이에 들어가지 않으면 **기본 줄바꿈으로 물러난다**.

3번이 핵심이다. 단어 중간 끊김을 막으면 단어가 통째로 다음 줄로 내려가 줄이 늘 수 있고 딱 맞게 조정된 패널에서는 그것이 곧 넘침이다. 이 규칙은 "지금 상자 안에 들어가던 글이 이 위젯 때문에 새로 넘치지는 않는다"를 보장한다.

`maxLines: 1`, `softWrap: false`, 한국어가 아닌 locale, 공백이 없거나 너무 많은 문장, 너비가 무한한 자리, 계산 결과가 공간에 안 맞는 경우에는 바로 `Text`처럼 그린다.

재는 값과 그리는 값은 같아야 한다. 그래서 위젯은 `DefaultTextStyle`의 `style`, `maxLines`, `overflow`, `softWrap`, `textAlign`, `textWidthBasis`, `textHeightBehavior`와 `MediaQuery`의 `textScaler`, `boldText`를 `Text`와 똑같은 순서로 풀어서 측정에 쓴다. `letterSpacingOverride`, `wordSpacingOverride`, `lineHeightScaleFactorOverride`도 스타일에 반영하고 줄 높이는 strut에도 반영한다. 그리기는 그 값들로 만든 `Text`의 `build` 결과를 그대로 돌려준다. 둘이 어긋나면 "줄이 늘지 않는다"와 "넘치지 않는다"가 함께 깨진다. SDK의 `Text.build`가 측정 방식을 바꾸면 이 경로도 함께 검토한다.

영어는 Flutter 기본이 이미 띄어쓰기에서 끊으므로 그대로 둔다. 일본어와 중국어는 글자 단위 줄바꿈이 관례라 기본 동작을 유지한다. locale별 모델은 `phraseModels` 인자로 끼울 수 있게 열어 두었고 지금은 한국어 모델만 들어 있다.

### 쓰면 안 되는 자리

측정에 실제 너비가 필요하므로 이 위젯은 `LayoutBuilder`를 쓴다. `LayoutBuilder`는 조상이 intrinsic 크기를 물으면 debug 빌드에서 단언으로 죽는다. 그래서 다음 아래에는 두지 않는다.

- `IntrinsicWidth`, `IntrinsicHeight`
- Material의 `AlertDialog`, `SimpleDialog` (안에서 `IntrinsicWidth`를 쓴다)

그런 자리에는 `Text`를 그대로 두거나, 화면을 이 프로젝트의 `GameModalCard` 계열 다이얼로그로 옮긴다. `test/widgets/semantic_text_usage_test.dart`가 한 파일 안에 `SemanticText(`와 위 이름이 함께 있으면 실패한다. 의도한 경우는 그 테스트의 허용 목록에 이유와 함께 적는다.

### 성능

- 결과를 (문자열, 스타일, strut, 정렬, 방향, textScaler, locale, `maxLines`, 너비 기준, 높이 동작, 너비, 높이)로 캐시한다. 키는 해시가 아니라 값으로 비교한다. 해시만 쓰면 충돌했을 때 다른 스타일의 배치를 그대로 돌려주고 그 경로는 다시 재지 않는다. 상한은 512개이고 가장 오래 안 쓴 항목부터 버린다.
- 캐시는 `phraseModels`를 생략한 기본 모델에만 쓴다. 기본 모델의 가중치는 const이고 level 목록은 불변이다. 외부 모델은 내부 weights나 levels가 바뀔 수 있으므로 캐시를 읽거나 쓰지 않는다. 같은 인스턴스를 다시 넘겨도 배치를 계산하며, 외부 모델을 자주 갱신하는 화면은 별도로 성능을 확인한다. spacing override는 반영된 스타일·strut가 캐시 키에 들어가므로 설정이 달라지면 이전 배치를 재사용하지 않는다.
- 가용 너비와 높이를 1 논리 픽셀 단위로 **내림**해서 키와 계산에 함께 쓴다. 크기 애니메이션 중에는 원시 값이 매 프레임 조금씩 달라 캐시가 매번 빗나가고 `TextPainter` 측정이 프레임마다 돈다. 내림은 안전한 쪽이다. 더 좁은 상자에 들어가는 배치는 실제 상자에도 들어간다.
- 측정에는 `TextPainter` 하나를 만들어 한 번의 계산 안에서 재사용하고 끝나면 `dispose`한다.
- 공백이 24개를 넘는 문장은 계산하지 않고 기본 줄바꿈에 맡긴다. 배치 탐색 비용이 공백 수의 제곱으로 늘기 때문이다.
- 상시 티커, `saveLayer`, 애니메이션 `Opacity`를 쓰지 않는다.

### 1차 범위 밖

`Text.rich`와 `RichText`는 다루지 않는다. 색이 다른 키워드나 숫자 span이 섞인 문장은 지금처럼 기본 줄바꿈으로 둔다. 조사 시점에 `lib/` 전체의 rich text 사용처는 `game_shared_battle_hud_widgets.dart` 한 곳뿐이고 그마저 `maxLines: 1`이라 줄바꿈이 일어나지 않는다. 다음 트랙에서 rich text 문장이 새로 생기면 그때 범위를 다시 본다.

`GameWordWrapText`(`lib/views/game/widgets/game_word_wrap_text.dart`)는 예전 단어 단위 줄바꿈 위젯이다. 튜토리얼 오버레이 한 곳에서 쓴다. 단어를 위젯으로 쪼개 `Wrap`에 넣는 방식이라 `find.text`와 접근성 label이 문장 단위로 잡히지 않는다. 새 화면에는 `SemanticText`를 쓰고 그 한 곳은 튜토리얼을 손보는 트랙이 정리한다.

### 출처와 라이선스

줄바꿈 알고리즘은 [semantic-wrap](https://github.com/woohyun-park/semantic-wrap) 0.4.0을 Dart로 옮긴 것이다. 한국어 모델 가중치는 같은 버전의 `@semantic-wrap/ko`에서 가져왔다. 둘 다 Apache-2.0이고 라이선스와 고지는 `third_party/semantic_wrap/`에 있다.

포팅에서 **뺀 것**은 다음과 같다. 모두 한국어 프리셋이 지나가지 않는 경로다.

- `characters` 경계 모드. 자소 분할이 필요하고 한국어 프리셋은 `spaces` 모드를 쓴다.
- `greedy`·`nearbyLayouts` 배치 계산기와 `consensus` 집계기. 기본값이 아니다.
- 중단·재개가 가능한 제너레이터 API, 진단 출력, 측정 일괄 처리.
- 브라우저 기본 배치와의 비교. Flutter는 기본 줄바꿈의 끊는 위치를 알려 주지 않으므로 선택기의 "기본 배치 없음" 분기만 탄다.

포팅이 원본과 같은 결과를 내는지는 `test/utils/semantic_wrap_fixture_test.dart`가 검사한다. 기준값은 원본 JavaScript 라이브러리를 실제로 돌려 만든 `test/fixtures/semantic_wrap_breaks.json`이고 만드는 스크립트는 `tools/semantic_wrap/generate_semantic_wrap_fixture.mjs`다. 한국어 예문 36개 × 너비 3종 = 108가지를 비교한다.

## 6. 테스트

`test/flutter_test_config.dart`가 모든 테스트 파일에서 한 번씩 돌며 한국어 번역을 전역 인스턴스에 적재한다. 개별 테스트는 따로 준비할 것이 없다.

Flutter는 테스트 파일에서 위로 올라가며 **가장 가까운** `flutter_test_config.dart` 하나만 쓴다. 그래서 하위 폴더에 설정이 따로 있으면 그 파일이 루트의 `applySharedTestSetup()`을 직접 불러야 한다. 지금은 `test/views/game/widgets/flutter_test_config.dart`가 그렇게 되어 있다.

화면 문구를 `find.text('한국어')`로 확인하는 기존 테스트는 고치지 않아도 된다. 전역 적재 덕분에 키 문자열이 아니라 한국어가 그대로 나온다. `Text`를 `SemanticText`로 바꾼 자리도 마찬가지다. `SemanticText`가 `Text`를 상속하고 `data`에 원문을 남기기 때문이다.

한 테스트 파일에서 `EasyLocalization`을 반복 mount할 때 비동기 asset 적재가 끝나기 전에 검사가 진행돼 빈 화면이 잡힐 수 있다. 한 앱을 유지하며 언어를 바꾸거나, 실제 번역 JSON을 동기 파일 읽기로 제공하는 테스트 전용 `AssetLoader`를 쓴다. `test/support/test_translations.dart`의 `TestTranslationAssetLoader`가 실제 병합 JSON을 동기 파일 읽기로 읽고 일반 async Future로 반환한다. JSON이 50KB를 넘으면 기본 asset loader가 isolate를 사용하므로 FakeAsync 안의 직접적인 언어 변경 await가 멈출 수 있다. 화면 테스트는 공용 로더를 사용하고, 자체 mock이나 전용 로더가 필요한 테스트는 기존 로더를 유지한다. 단순히 settle 횟수를 늘려 문제를 덮지 않는다.

## 7. 남은 하드코딩과 회귀 방지

`test/tools/no_hardcoded_korean_test.dart`가 `lib/`의 문자열 리터럴에 한글이 있으면 실패한다. 아직 옮기지 못한 파일은 그 테스트의 허용 목록에 있다. 목록은 줄어들기만 한다. 한 트랙이 자기 영역의 파일을 끝내면 같은 변경에서 그 파일의 줄을 지운다.

주석, `debugPrint`·`print` 인자, `assert` 메시지, `lib/services/debug_run_fixture_*.dart`는 검사 대상이 아니다. 플레이어가 보지 않는 문구이기 때문이다.
